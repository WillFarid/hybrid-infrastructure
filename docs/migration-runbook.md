# Migration runbook: on-premises Windows file services to AWS

**Scope:** move the file services of the on-premises domain `corp.example.com` to the AWS environment built in this repository (VPC `10.2.0.0/16`, Managed AD `cloud.example.com`, FSx for Windows).

**Status:** written from experience and the AWS documentation, **not executed**, because the lab is plan-only. The commands are the ones I would run, and each one should be verified in a test environment before a real cutover. Items marked **VERIFY** depend on behavior I could not test offline.

## 0. Roles and prerequisites

| Item | Needed before starting |
|---|---|
| On-premises | Domain admin rights. A VPN-capable device with a public IP. Inventory of shares, sizes and permissions. |
| AWS | The Terraform in this repository applied. Administrator access to the directory and the file system. |
| Address plan | VPC `10.2.0.0/16` and on-premises `192.168.0.0/16` do not overlap (enforced by a Terraform validation). |
| Maintenance window | Agreed cutover window, plus a rollback decision point. |

## 1. Assess

1. List every share and its size: `Get-SmbShare | Where-Object { $_.Special -eq $false }` and `Get-ChildItem <path> -Recurse | Measure-Object -Property Length -Sum`.
2. Record share-level and NTFS permissions. `icacls <path> /save perms.txt /t` captures the NTFS ACLs for comparison later.
3. Identify open files and heavy users, and who owns each share. Agree the freeze time per share.
4. Confirm that no share depends on a hard-coded server name. Those must be re-pointed through DFS or a DNS alias.

## 2. Connect the networks

1. Configure the on-premises device from the VPN configuration file downloaded from the AWS console for the connection. The pre-shared keys are generated by AWS and are not in the code.
2. Bring up both tunnels and confirm both show **UP**. Check the VPN tunnel logs in CloudWatch if not.
3. Verify routing. On a test machine: `Test-NetConnection <aws-server-ip> -Port 445` and `ping`. Confirm return traffic: the on-premises route table must send `10.2.0.0/16` to the VPN device.
4. Check the maximum packet size across the tunnel. Large SMB transfers expose MTU problems first.

## 3. DNS, in both directions

DNS is what breaks first and what everything else depends on. Test it before touching identity.

1. On an on-premises domain controller, create a conditional forwarder for `cloud.example.com` pointing at the two Managed AD domain controller addresses (from the `directory_dns_ips` output):
   `Add-DnsServerConditionalForwarderZone -Name "cloud.example.com" -MasterServers <dc-ip-1>,<dc-ip-2>`
2. The AWS side already has the reverse: a conditional forwarder for `corp.example.com` to `192.168.1.10`, plus the Route 53 Resolver outbound rule (both created by Terraform).
3. Test from both sides:
   - On-premises: `Resolve-DnsName <aws-server-name>.cloud.example.com`
   - On an AWS server (Session Manager): `Resolve-DnsName dc01.corp.example.com`
4. For AWS service names, point an on-premises forwarder at the two **inbound resolver endpoint** IPs (`dns_inbound_endpoint_ips` output).
5. **VERIFY:** Managed AD forwards names it does not own to the Amazon-provided resolver. Confirm with `Resolve-DnsName ssm.us-east-1.amazonaws.com` on an AWS server and check that it returns a private endpoint address.

## 4. Identity: trust the two domains

A one-way or two-way forest trust lets on-premises users authenticate to AWS resources without duplicating accounts.

1. Confirm the AD ports from `192.168.0.0/16` to the AWS domain controllers (opened by Terraform): `Test-NetConnection <aws-dc-ip> -Port 389`, then `-Port 88`, `-Port 445`.
2. Create the trust from the AWS Directory Service console: trust type **Forest**, direction **two-way** (or one-way incoming if AWS resources only need to trust on-premises users), remote domain `corp.example.com`, with a trust password.
3. Create the matching trust on the on-premises domain in **Active Directory Domains and Trusts**, using the same password.
4. Verify: `nltest /domain_trusts` and `netdom trust cloud.example.com /domain:corp.example.com /verify`.
5. Test a real authentication: log on to an AWS server with an on-premises account (`CORP\username`) and run `klist` to see the Kerberos tickets.

## 5. Prepare the servers and the share

1. Confirm the two Windows servers joined `cloud.example.com`: `(Get-WmiObject Win32_ComputerSystem).Domain`. If an instance did not join, run the SSM association again from the console and check the association execution output.
2. Rename the servers if required (they keep AWS's default hostnames). Do it before any share or service depends on the name.
3. **VERIFY:** administrators can manage FSx. Add the migration administrators to the delegated FSx administrators group in the AWS domain.
4. Connect to the file system for administration with remote PowerShell, then enforce encrypted SMB sessions. **VERIFY** the cmdlet names against current FSx documentation, for example `Set-FsxSmbServerConfiguration -RejectUnencryptedAccess $true`.
5. Create the shares on FSx to mirror the source names, and set share permissions.

## 6. Move the data

Do an initial bulk copy while users are still working, then a short final sync during the cutover window.

1. Initial copy, from a server with access to both sides:
   `robocopy \\source\share \\<fsx-dns-name>\share /MIR /COPYALL /DCOPY:DAT /R:1 /W:1 /MT:16 /LOG:C:\migration\share-initial.log /TEE`
   `/COPYALL` carries NTFS ACLs, owners and auditing information. `/MIR` mirrors, so use it only toward an empty or previously synced target.
2. Review the log for failures. Fix locked files and path-length problems.
3. **Cutover window:** make the source read-only (or disconnect users), then run the same robocopy command once more as the final sync.
4. Compare: file count and total size on both sides, and a sample of permissions with `icacls`. Compare against the `perms.txt` from the assessment.
5. Alternative for large data sets: AWS DataSync.

## 7. Cutover

1. Re-point users. Preferred: a DFS namespace, so the path users see (`\\corp.example.com\files`) stays the same and only the folder target changes. Otherwise, update mapped drives through Group Policy.
2. Test with a pilot group first: open, edit, save, and check permissions on a few real files.
3. Monitor for 24 to 48 hours: the FSx audit log in CloudWatch for denied access, and the help desk queue.

## 8. Rollback

**Decision point:** if the pilot fails permission or performance checks, or the final sync does not complete inside the window, roll back.

1. Re-point the DFS target (or the mapped drives) back to the on-premises share.
2. Re-enable write access on the source.
3. Anything written to FSx during the window must be copied back (`robocopy` in the reverse direction) before the source is trusted again.
4. Keep the source read-only and intact until the agreed hold period has passed. **Do not decommission it early.**

## 9. After the migration

- Keep the source for the agreed hold period, then retire it.
- Confirm FSx automatic backups run, and do one test restore.
- Review the audit log and the VPN tunnel logs weekly for the first month.
- Update the inventory and the network documentation.
